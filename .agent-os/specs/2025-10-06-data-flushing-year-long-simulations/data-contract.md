# Data Contract: Checkpoint Format

## Overview

Checkpoint files contain complete simulation state at a specific point in time, enabling both data analysis and simulation resumption. The format extends the standard dataset structure with checkpoint-specific metadata.

## Field Definitions

### Checkpoint Metadata

- `day`: Simulation day when checkpoint was created (1-based)
- `timestamp`: ISO 8601 timestamp of checkpoint creation
- `trigger`: Reason for checkpoint (`interval`, `memory`, `manual`)
- `memoryUsage`: Memory statistics at checkpoint time (Node.js process.memoryUsage() format)
- `version`: Checkpoint format version for compatibility
- `checksum`: SHA256 hash of simulation data for integrity verification

### Simulation Data

The `simulation` object contains the complete dataset structure as generated by the standard simulation process, with `simulationCompleted` set to `false` for checkpoints.

## File Naming Convention

```
checkpoint-day-{DAY:03d}-{TIMESTAMP}.json
```

Examples:

- `checkpoint-day-030-2025-10-06T12-00-00.json`
- `checkpoint-day-060-2025-10-06T18-30-15.json`

## Validation Rules

### Required Fields

- All fields in the checkpoint metadata must be present
- Simulation config must match the original run configuration
- Daily results array must contain exactly `day` number of entries

### Data Integrity

- Checksum must validate against the simulation data
- Memory usage values must be reasonable (>0, < container limits)
- Timestamp must be within simulation runtime window

### Compatibility

- Version field enables format evolution
- Unknown fields should be preserved during read/write cycles
- Breaking changes require version increment

## Merge Process

When combining checkpoints with final state:

1. Load all checkpoint files in chronological order
2. Validate checkpoint chain continuity (day numbers sequential)
3. Merge daily results arrays from all checkpoints
4. Update summary statistics with final values
5. Set `simulationCompleted: true`
6. Generate final checksum

## Error Handling

### Corruption Detection

- Invalid JSON structure → reject checkpoint
- Checksum mismatch → log warning, attempt repair
- Missing required fields → reject checkpoint

### Recovery Strategies

- Use previous checkpoint if current is corrupted
- Reconstruct missing data from adjacent checkpoints
- Fall back to simulation restart from beginning

## Performance Considerations

### File Size

- Typical 30-day checkpoint: 5-10MB
- 365-day final dataset: 50-100MB
- Compression ratio: 3:1 with gzip

### I/O Patterns

- Write: Streaming JSON serialization
- Read: Memory-mapped file access for large checkpoints
- Merge: Incremental processing to avoid loading all checkpoints simultaneously</content>
